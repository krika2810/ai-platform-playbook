Basics of Platform: what a platform actually is

Source reel: instagram.com/reel/Dcck0sXtqNE (3 min 45 s) - posted twice, also as reel/DcckU0kBvLf

What he says in the reel A platform is the layer between infrastructure and application. Picture a cake: the bottom layer is infrastructure, the cream and cookies in the middle are the platform, the decoration on top is the application. In the classic world, a platform architect builds the tools application teams need to run on something like OpenShift. In the AI world, the platform architect must know how to provision GPUs, deploy LLMs on top, and support application teams running AI agent apps. With 10 to 15 lines of business each building agent apps, the platform architect must build common tools all of them share - an internal developer platform - so duplicate work disappears.

The idea, explained

Most people who "work in tech" work on one of three layers, and being clear about which layer you are on changes every design decision you make.

The infrastructure layer is raw capacity: servers, GPUs, networks, storage. It answers the question "what compute do we have?" The application layer is what the business actually wanted: the customer-support agent, the document-summarizing tool, the sales-copilot. It answers "what does the user get?" The platform layer sits between them and answers a third question: "how does an application team get from raw compute to a running, reliable app without becoming infrastructure experts?"

That middle layer is easy to underestimate because when it works, nobody notices it. In the classic cloud world, platforms like OpenShift or Kubernetes distros did this job: an app team shipped code, and the platform handled deployment, scaling, logging and secrets. The app team never thought about load balancers or node pools.

AI changes what the platform must provide. An application team building an AI agent needs things a classic platform never offered: GPU capacity carved out for them, a deployed LLM endpoint they can call, a vector database, a way to register tools the agent can use, somewhere to keep prompts, and a way to test whether the model's answers are any good. If the platform does not offer these as shared services, every team builds its own version - badly, and five times over.

That is the punchline of Episode 1, and honestly of the whole series: the AI platform architect's job is to build an internal developer platform (IDP) for AI. "Internal" because its customers are your own developers. "Platform" because it is built once and used by every team. When 10 to 15 lines of business each need an agent app, the choice is not "15 teams build 15 apps." It is "15 teams build 15 apps, and either 15 copies of the plumbing or one."

Why it matters

  • Duplicated plumbing is invisible waste. Every team that builds its own document pipeline, its own prompt store, its own model gateway is spending engineering months the company pays for more than once.
  • The platform is a product, not a project. It has customers (your developers), a roadmap, and adoption as its success metric. Episode 1 is where that framing starts.
  • Your role definition follows the layer. An AI platform solution architect is not the person building the agent app. They are the person making it cheap and safe for fifteen teams to build theirs.

The Centralized MCP Hub

Source reel: instagram.com/reel/DcgefFpJdoC (1 min 14 s)

What he says in the reel In an enterprise, multiple lines of business work on different AI projects. If one LOB builds an MCP server to connect to a DB2 database, the other LOBs need to know it exists - otherwise you end up with duplicate MCP servers doing the same job. As an AI platform architect, build a centralized MCP Hub: produce MCP servers based on each LOB's requirements, host them in one central location, and let every team use them. It avoids duplicate work and saves the organization real cost.

The idea, explained

An AI agent is only as useful as the systems it can reach. Model Context Protocol (MCP) is the emerging standard for making those connections.

Before MCP, connecting an LLM to a company system meant bespoke work every time: custom function-calling schemas, custom glue code, custom auth handling. MCP standardizes this. An MCP server wraps a system - say a DB2 database, a ticketing tool, or a document store - and presents it to any MCP-aware agent in a uniform way: "here are the tools I offer, here is how to call them."

Now picture the enterprise without a hub. Team A needs DB2 data, so they write a DB2 MCP server: connection handling, credentials, query tools, tests, deployment. Three months later Team B needs the same database, does not know Team A's server exists, and builds it again. Multiply by every database and every SaaS tool in the company, and you get dozens of near-identical connectors, each with its own bugs, its own security posture, its own on-call burden.

The centralized MCP Hub is the platform answer: one team (the platform team) builds and hosts the MCP servers as shared services. A hub gives you four concrete benefits. Discovery: a team can look up "is there already a connector for this system?" before building anything. Security review once: credentials, network rules and audit logging are vetted a single time by people who own that risk, instead of fifteen times with fifteen levels of care. Maintenance once: when the DB2 driver changes, one server gets patched, not fifteen. Cost: one deployment to run and monitor, not a fleet of forgotten duplicates.

Why it matters

  • Connectors are infrastructure, not features. The hub treats them as shared platform services, owned and operated centrally.
  • The registry is as valuable as the servers. "What do we already have?" being answerable in one search is what actually stops duplication.
  • This is the same pattern as Episode 1's IDP applied to integrations: build once, share with every LOB.
Season 2 - Episode 3 - Aug 27, 2026

Multi-tenant Service Platform Architecture

Source reel: instagram.com/reel/DcjG3YWy0jc (1 min 19 s)

What he says in the reel Multiple LOBs build AI projects, and they all need a platform. One platform per LOB is a cost overhead, so you need one centralized AI platform they all share. Four design principles make that work: (1) hard tenant isolation so each LOB only touches its own area, (2) usage metering per LOB so consumption is measurable, (3) custom rate limiting per LOB, and (4) a model routing gateway that prioritizes usage so the right service reaches the right LOB.

The idea, explained

Sharing one platform across the whole company is the cost-efficient answer - but sharing without design is how one team's experiment takes down everyone else's production.

Hard tenant isolation means each LOB's data, prompts, documents and workloads are separated by construction, not by politeness. In practice: separate namespaces or accounts, separate API keys, separate vector indexes, no shared caches that could bleed one tenant's data into another's answer. "Hard" is the key word. If isolation depends on developers remembering to filter by customer ID, it will eventually leak. AI makes this sharper than classic multi-tenancy, because a retrieval system that mixes tenants' documents does not just expose rows in a table - it can speak one LOB's confidential data into another LOB's chat window.

Usage metering means measuring consumption per tenant: tokens processed, GPU minutes, vector storage, number of agent runs. This is not only about billing teams back (though chargeback changes behavior fast). It is how you learn which LOB is about to hit its limits, which workloads are unexpectedly expensive, and whether the platform is actually getting adopted.

Custom rate limiting per LOB is the safety valve. Without it, one team's load-test or runaway agent loop can saturate the shared model endpoints and every other tenant's app slows down. Per-tenant quotas - requests per minute, tokens per day - keep the platform fair and keep one tenant's incident from becoming everyone's incident.

The model routing gateway ties it together. Every LLM call in the company flows through one gateway, which decides where each request goes: an expensive frontier model for a hard reasoning task, a small cheap model for classification, a priority lane for the LOB running a customer-facing launch. This gives the platform team one place to enforce policy, control cost, fail over when a provider degrades, and upgrade models without asking fifteen teams to change code.

Why it matters

  • These four principles are a checklist. Isolation, metering, rate limits, routing - a shared AI platform missing any one of them will either be unsafe, unaffordable, or unfair.
  • Multi-tenancy is what makes the economics work. It is the reason "one platform for everyone" beats "one platform each."
  • The gateway is the control point. Whoever owns routing owns cost, priority and policy for the whole company's AI usage.
Season 2 - Episode 4 - Aug 31, 2026

The Centralized Prompt Registry

Source reel: instagram.com/reel/DctVc2ZPeNV (1 min 27 s)

What he says in the reel Prompts fall into two major categories: system prompts and application-code-generated prompts. You must decouple the two. System prompts should be separated out, tested, versioned and deployed deliberately. Application-generated prompts also need to be separated, versioned, stored in a repository, and pulled from there when needed. Managing and decoupling these two prompt types - versioning them, storing them in a registry, deploying them - is the AI platform architect's responsibility.

The idea, explained

In most companies today, the most behavior-critical text in the entire AI system is sitting as a string literal inside some application's source code. That is the problem this episode is about.

A system prompt is the standing instruction set: who the model is, what it may and may not do, how it should format answers. It is effectively policy written in English. An application-generated prompt is what the code assembles per request: the user's question plus retrieved documents, conversation history, and templated instructions stitched together at runtime.

Why decouple them? Because they change for different reasons, at different speeds, owned by different people. A system prompt changes when policy or behavior needs to change - and that change should go through review and testing like any policy change. An application prompt is assembled by code and changes with the code. Hard-coding both into the app means a wording fix to the assistant's tone requires a full application release, and nobody can answer "what instructions is production running right now?"

A prompt registry treats prompts as versioned assets, the way an artifact repository treats binaries. Each prompt has a name, versions, a changelog, test results, and a deployment state ("v7 is live for the support agent, v8 is in testing"). That unlocks things hard-coded prompts can never do: rollback when a prompt change degrades answers, A/B comparison between versions on real traffic, review workflow so a domain expert can improve wording without touching code, and audit - when the model said something wrong last Tuesday, you can see exactly which instructions it was running.

Notice how this connects to the evaluation platform in Episode 7: versioned prompts in a registry are what make prompt changes testable in CI, instead of vibes.

Why it matters

  • Prompts are configuration and policy, not code. Manage their lifecycle the way you manage any other production asset.
  • "Which prompt produced that answer?" must be answerable. Versioning is what makes AI behavior auditable.
  • Decoupling unlocks speed. The people best at improving prompts are often not the people who deploy the app.

Agent SDK Standardization

Source reel: instagram.com/reel/Dc0xH_jNX75 (1 min 32 s)

What he says in the reel You have standardized the MCP hub and the centralized prompt registry. Now focus on the agent SDK. An agent SDK gives you the standards, documentation, procedures and best practices for implementing agent solutions in your organization. Every serious organization has one - Claude has the Claude Agent SDK - and you can take a standard SDK like that and customize it for your needs. As the AI platform solution architect, designing the standard agent SDK for your LOBs is your responsibility.

The idea, explained

An agent SDK answers a deceptively simple question: when a developer in your company sits down to build an AI agent, what do they start from?

Without a standard, each developer starts from a tutorial. One team builds agents as Python scripts with raw API calls and hand-rolled retry logic. Another uses a framework with completely different conventions. A third copy-pastes something from a hackathon. Six months later the company has fifteen agent codebases that share nothing: different logging, different error handling, different ways of calling tools, different levels of security care. Nobody can maintain anyone else's agent, and every review starts from zero.

A standard agent SDK fixes the shape of the solution before anyone writes business logic. A good one typically includes: scaffolding (a new agent starts from a template with the right project structure), tool interfaces (one blessed way to connect tools - in this series, through the MCP hub), memory and state patterns (how conversation context is stored and retrieved), observability (every agent run logs its steps, tool calls and token usage in a format the platform can collect), guardrail hooks (standard places to insert safety checks), and evaluation hooks (every agent built on the SDK can be plugged into the Episode 7 evaluation pipeline without extra work).

His point about customization is practical: you do not have to invent this from nothing. Vendor SDKs (he names the Claude Agent SDK) encode tested patterns for tool use, agent loops and context management. The platform architect's job is to adopt one as the base, wrap it in the organization's own conventions - naming, auth, logging destinations, approved models through the routing gateway - and publish that as "the way we build agents here."

Why it matters

  • Standardization is what turns agents from experiments into a portfolio. Fifteen agents built one way can be operated; fifteen built fifteen ways cannot.
  • The SDK is where the platform's other services get adopted. If the template wires in the MCP hub, prompt registry and evaluation hooks by default, teams use them without being told to.
  • Onboarding speed is the visible win. A new team's first agent goes from weeks of framework decisions to days of filling in business logic.
Season 2 - Episode 6 - Sep 4, 2026

RAG as a Service

Source reel: instagram.com/reel/Dc3yyC4ROi2 (1 min 49 s)

What he says in the reel Different teams build AI projects with different architectures - RAG, ReAct, human-in-the-loop. Every team doing RAG ends up building the same key components: a document pipeline, vector indexing, and hybrid search (dense and sparse). When many teams each build these, the platform gets messy. The fix: provision RAG as a Service - document pipeline, vector indexing and hybrid search exposed as API calls - so no team builds redundant mechanisms. Think about offering RAG as a Service, or even ReAct as a Service, to your development teams.

The idea, explained

RAG is how an AI answers questions from your company's own documents: find the relevant pieces, hand them to the model, and let it answer from them. It is the most common enterprise AI pattern - and the one most often rebuilt from scratch by every team that needs it.

Under the hood, every RAG system has the same three machinery layers he names. The document pipeline takes raw content - PDFs, wikis, policy docs - and prepares it: extracting text, splitting it into chunks, and computing an embedding for each chunk. Vector indexing stores those embeddings in a database built for similarity search, so "find chunks about refund policy" becomes a fast lookup. Hybrid search combines two retrieval styles: dense search (embedding similarity - good at meaning, so "money back" finds "refund") and sparse search (keyword matching like BM25 - good at exact terms like part numbers and error codes). Neither alone is reliable; together they cover both ways people phrase things.

Each of these layers has real depth: chunking strategy changes answer quality, index tuning changes latency, hybrid ranking needs weighting. When every application team implements this stack independently, you get the Episode 2 problem again, squared: five document pipelines with five different chunking bugs, five vector indexes to operate, five search quality levels. And the team building the customer-support agent - whose actual job is the agent - is instead spending its quarter on retrieval plumbing.

RAG as a Service turns the whole stack into platform APIs: "ingest these documents into collection X" and "query collection X with this question, hybrid mode." Teams get retrieval as a dependency, the way they get databases today. The platform team owns chunking defaults, index operations and search quality tuning once, centrally, and every consumer benefits from every improvement. His aside about ReAct as a Service generalizes the thought: any agent pattern every team rebuilds (the ReAct reasoning loop, human-in-the-loop approval flows) is a candidate for the same treatment.

Why it matters

  • Retrieval quality is a platform concern. Centralizing it means one team gets very good at chunking, indexing and ranking - instead of every team getting mediocre at it.
  • The API boundary is the point. Application teams think in questions and answers; the platform thinks in pipelines and indexes.
  • Watch for the pattern, not just RAG. Anything three teams have each built once belongs on the platform roadmap.

The Enterprise Evaluation Platform

Source reel: instagram.com/reel/Dc_b2DQSNwn (59 s)

What he says in the reel One of the critical tasks in any GenAI or agent project is evaluating the LLM's output. Do it effectively: build an automated pipeline using LLM-as-a-judge architecture, use curated datasets with ideal outputs, and run semantic regression tests in the continuous integration pipeline. Then you can properly evaluate the LLM and hand a reliable foundation to the teams building agent projects.

The idea, explained

Classic software testing asks "does the output equal the expected output?" AI breaks that question. Ask an LLM the same thing twice and you get two different phrasings - both possibly correct. So how do you test it? This episode is the platform answer.

The first tool is LLM-as-a-judge: since a model's output is open-ended text, use another model to grade it. The judge gets the question, the system's answer, and a rubric - "is this answer correct, grounded in the provided documents, and appropriately concise?" - and returns scores. It is not perfect, but it scales: thousands of answers graded in minutes, consistently, where human review covers a handful.

The second tool is the curated dataset, often called a golden set: a carefully built collection of representative inputs with ideal outputs, reviewed by humans who know the domain. "Here are 200 real support questions and what great answers look like." This dataset is the yardstick everything else measures against. Building it is unglamorous and absolutely load-bearing - an evaluation pipeline is only as trustworthy as its golden set.

The third tool is where it becomes engineering: semantic regression tests in CI. On every change - a new model version, a prompt update from the Episode 4 registry, a retrieval tweak - the pipeline runs the golden set through the system, the judge scores the outputs, and semantic comparison checks answers against the ideal ones (meaning-equivalent counts as passing; exact string match is neither possible nor desired). If quality drops below the bar, the change does not ship, exactly like a failing unit test. "Regression" is the key word: the goal is to catch the moment a change that improved one thing quietly broke three others.

As a platform capability, this is offered to every team the way the other services are: register your agent, point at your golden set, get evaluation runs on every change and dashboards over time. Nobody should be shipping prompt or model changes on instinct.

Why it matters

  • Evaluation is what makes AI changes deployable. Without it, every model upgrade or prompt edit is a gamble discovered by users.
  • The golden set is an asset. Curate it with domain experts, grow it from real failures, protect it.
  • Automation is the difference between testing and theater. If evaluation is not in CI, it happens once and never again.

The Unified Tool Catalog

Source reel: instagram.com/reel/DdCAKP-hisW (1 min 56 s)

What he says in the reel Application teams building AI agents spend a lot of time writing instructions so LLMs can use their systems - "prompt wrapping." Instead of doing this manually, use MCP as an auto-translator: convert existing REST APIs and OpenAPI standards into a form LLMs understand easily, and build a tool catalog - a library. When the AI development team connects to this unified tool catalog, the LLM can see how to connect to the local database or local software through MCP servers and execute the task successfully.

The idea, explained

An agent acts on the world through tools: callable actions like "look up an order," "create a ticket," "run this query." Episode 8 is about where those tools come from, and why nobody should be writing them by hand.

The manual approach he warns against - writing per-integration prompt instructions and glue for every system - has three failure modes. It is slow: every team hand-describes the same APIs for their own agents. It drifts: five hand-written descriptions of the same API diverge, and each agent behaves slightly differently against the same system. And it rots: when the API changes, somebody has to remember every place its description was embedded.

Here is the leverage most enterprises are sitting on: their systems are already described. Decades of REST APIs come with OpenAPI specifications - machine-readable documents listing every endpoint, parameter and response. MCP tooling can read an OpenAPI spec and generate the corresponding tool definitions automatically: the endpoint becomes a tool, the parameters become its schema, the descriptions become what the LLM reads to decide when and how to call it. The "auto-translator" framing is exact: from API-speak to LLM-speak, without a human rewriting anything.

The unified tool catalog is where those generated tools live: one library, browsable by every team - "we have tools for orders, inventory, ticketing, the DB2 reporting database" - each backed by the MCP servers from Episode 2's hub. An application team building an agent stops integrating systems and starts selecting capabilities from a catalog. The LLM gets accurate, current tool definitions; the platform team gets one place to version, secure and audit every tool in the company.

Notice the series closing its own loop here: the tool catalog (Ep 8) sits on the MCP hub (Ep 2), is consumed through the standard agent SDK (Ep 5), shared safely across LOBs by the multi-tenant design (Ep 3), and kept honest by the evaluation platform (Ep 7). It is one platform, explained one reel at a time.

Why it matters

  • Your API specs are a head start. OpenAPI-to-tool generation turns years of existing documentation into agent capability almost for free.
  • Generated beats handwritten. Tools derived from the spec stay correct as APIs evolve; hand-written prompt glue silently rots.
  • A catalog changes the team's job from "integrate systems" to "compose capabilities" - which is where the business value actually is.
Career advice - Aug 23, 2026

"Don't Do This": experienced developers and architects, don't start over

Source reel: instagram.com/reel/DcXSYZDyqhI (2 min 54 s)

What he says in the reel Do not get overwhelmed by the flood of AI courses, tools and certifications from every company. Do a self-analysis of your base experience first. If you have 10 years as a developer, that experience cannot be replaced by AI - companies need it to implement AI solutions. Pick AI tools that elevate your base experience, not overwrite it. Developers: learn AI integrations in your IDE and automation in your core toolchain. Cloud architects: do not drop everything to chase a generic AI certification - learn the AI services of your cloud provider and build AI architecture on top of the expertise you already have.

The idea, explained

The anxiety is real: every week brings a new model, a new framework, a new certification track, and a new wave of "learn this or be left behind." His advice cuts through it with one move - anchor on what you already are.

The logic is about where value actually sits. A company adopting AI does not need fifteen thousand people who all took the same introductory AI course. It needs people who understand its systems, its data, its customers - and can now also apply AI there. Ten years of knowing how this organization's software actually works, where the bodies are buried, and why that integration is fragile, is precisely the context that makes someone's AI work land in production instead of in a demo. The model is interchangeable; the context is not.

So the learning strategy is additive, not replacement. A developer asks: "how does AI plug into how I already build?" - AI assistance in the IDE, AI-driven test generation, automation in the existing toolchain. A cloud solution architect asks: "what AI services does my cloud provider offer, and how do they compose into the architectures I already design?" Someone with a decade on AWS who learns AWS's AI services is immediately dangerous in a way that a person with a fresh generic certification and no architecture scar tissue is not.

There is a second, quieter benefit: this path is finite. "Learn all of AI" is an endless, demoralizing curriculum. "Learn the AI capabilities adjacent to my existing expertise" is a bounded one you can actually finish - and each new thing connects to something you already understand, which is how learning sticks.

How to apply it

  • Write down your base experience in one sentence ("10 years, backend, payments systems"). Every AI learning decision gets judged against it: does this make that sentence more powerful?
  • Map AI onto your current tools first - your IDE, your cloud, your framework - before touching anything outside your stack.
  • Treat certifications as a means, not the goal. The goal is AI applied to your domain; a cert is worth doing only if it serves that.

Reference

Glossary: every key term in one place

AI platformThe shared layer between infrastructure and applications that gives every team common AI services: models, tools, retrieval, prompts, evaluation.
Internal developer platform (IDP)A company's internal self-serve product for its own developers: environments, pipelines and services consumed without tickets or waiting.
LOB (line of business)A distinct business unit inside an enterprise - retail, insurance, support - each building its own applications on the shared platform.
MCP (Model Context Protocol)An open standard for connecting LLM applications to external tools and data in a uniform way, replacing custom per-integration glue.
MCP serverA service that wraps one system (database, API, file store) and exposes it to agents through MCP: listing its tools and executing them.
MCP HubA centralized, governed home hosting all of an organization's MCP servers, so connectors are discovered and reused instead of rebuilt.
Tool callingThe mechanism where an LLM requests a concrete action ("call get_order_status") instead of just replying in text, and the system executes it.
OpenAPIA machine-readable standard describing a REST API's endpoints, parameters and responses - the raw material tools are generated from.
Unified tool catalogA central library of LLM-ready tools, generated from API specs via MCP, that every agent team composes from instead of hand-integrating.
System promptThe standing instructions defining an LLM's role, rules and boundaries for every request - policy written in English.
Prompt registryA versioned store for prompts, managed like release artifacts: tested, reviewed, deployed, and answerable to "which version ran when?"
Multi-tenancyOne platform serving many business units, with hard isolation between each tenant's data, prompts and workloads.
Usage meteringMeasuring each tenant's consumption (tokens, GPU time, storage) for cost visibility, limits and adoption tracking.
Rate limitingPer-tenant quotas on requests or tokens, so one team's spike or runaway agent cannot degrade the shared platform for everyone.
Model routing gatewayA single entry point for all LLM traffic that picks the right model per request by cost, capability, tenant priority and load.
RAGRetrieval-Augmented Generation: retrieve relevant documents first, then have the LLM answer grounded in them instead of its memory.
Document pipelineThe machinery that turns raw documents into searchable knowledge: text extraction, chunking, embedding.
EmbeddingA numerical vector capturing a text's meaning, so semantically similar texts can be found by mathematical similarity.
Hybrid searchRetrieval combining dense (embedding/meaning) and sparse (keyword/BM25) search, covering both paraphrases and exact terms.
Agent SDKThe standard kit for building agents in an org: scaffolding, tool interfaces, memory patterns, logging and evaluation hooks.
ReActAn agent pattern that interleaves reasoning steps and tool actions: think, act, observe, repeat until done.
LLM-as-a-judgeUsing a second LLM to grade the first's outputs against a rubric, so evaluation scales beyond human review.
Golden datasetA curated set of representative inputs with expert-reviewed ideal outputs - the yardstick all evaluation measures against.
Semantic regression testA CI check that fails a change when answer quality drops by meaning (not exact string match), catching quiet AI regressions.
